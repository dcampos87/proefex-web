Estado: `PHASE_3_2_WEB_DATA_LAYER_COMPLETE — REQUIRES_PROEFEX_INPUT (endpoints/claves)`
Alcance: **solo `proefex-web`**. Prerequisito real de A5.

A5 (**revalidación**) sigue `BLOCKED — ARCHITECTURE DECISION REQUIRED` (AGENTS §20/§43):
esta fase **no** crea `/api/revalidate`, **no** usa `revalidateTag`/`revalidatePath`, **no**
etiqueta el cache, **no** toca OpenNext/Wrangler/infraestructura y **no** toca
`proefex-cms`/`proefex-api`/`proefex-infrastructure`.

## 1. Qué se construyó

```
page / server component          (src/app/**)
        ↓  sólo funciones de dominio
src/lib/content                  listContent · getContentEntry · getHomePage · getNavigation · getSiteSettings
        ↓  tags derivados (A5-ready, sin aplicar)
src/lib/api                      config · client · errors · request-id · types · validators
        ↓  único punto HTTP (fetch con X-Request-Id, ETag, timeout, RFC 7807)
proefex-api  →  Supabase
```

Archivos nuevos:

| Archivo | Responsabilidad |
|---|---|
| `src/lib/api/config.ts` | Base URL + entorno (dev/staging/prod), normalización y validación fail-closed |
| `src/lib/api/client.ts` | Único `fetch` al API: cabeceras, `X-Request-Id`, `If-None-Match`, timeout, `cache`, RFC 7807 |
| `src/lib/api/errors.ts` | `ApiError` con `kind` cerrada (`not-found`, `rate-limited`, `server`, `invalid-response`…) |
| `src/lib/api/request-id.ts` | Generación/normalización de `X-Request-Id` (patrón del API) |
| `src/lib/api/types.ts` | DTOs del contrato público (derivados, no del esquema Supabase) |
| `src/lib/api/validators.ts` | Validación estructural de respuestas y parseo tolerante de RFC 7807 |
| `src/lib/content/index.ts` | Capa de dominio: rutas, outcomes y tags por lectura |
| `src/lib/content/tags.ts` | Catálogo determinista de tags (idéntico al del API) |
| `src/components/content/ContentSummaryList.tsx` | Lista editorial de contenido publicado (sin destinos aún) |
| `src/components/content/SectorDetailView.tsx` | Vista de detalle de sector con contenido del CMS |
| `tests/*.test.ts` | 43 tests con el runner nativo de Node (sin dependencias nuevas) |

Archivos modificados: `package.json` (script `test`), `tsconfig.json`
(`allowImportingTsExtensions`, requerido para que `src/lib` sea ejecutable por el runner de
Node), `src/app/globals.css` (`.ed-row--static`), `src/app/casos/page.tsx`,
`src/app/insights/page.tsx` y los 8 `src/app/sectores/<slug>/page.tsx`.

Convención: `src/lib/**` usa imports relativos con extensión `.ts` explícita. Es un
requisito de Node para TypeScript ESM y permite testear la capa sin transpiladores,
loaders ni dependencias nuevas.

## 2. Contrato del API realmente usado

Verificado en `proefex-api` (commit `0d3cbee`, módulo `content`), no inferido de docs
históricos ni de `@proefex/blocks-schema` (desalineado, AGENTS §24).

| Endpoint (`/v1`) | Uso en Web | Estado |
|---|---|---|
| `GET /content/:type` | listados de casos e insights | **usado** |
| `GET /content/:type/:slug` | detalle de sector | **usado** |
| `GET /content/pages/home` | home editorial del CMS | implementado, sin consumir todavía |
| `GET /content/navigation` | navegación publicada | implementado, sin consumir todavía |
| `GET /content/settings` | configuración pública del sitio | implementado, sin consumir todavía |

`navigation` y `settings` existen en el contrato (y su webhook de invalidación está
declarado como `PROEFEX_DISABLED_WEBHOOK_TYPE` en el API), pero **hoy el CMS no los
publica**: consumirlos en `Header`/`Footer` cambiaría el HTML de todas las rutas sin
contenido detrás (AGENTS §41). Quedan implementados y probados, listos para activarse.

Del contrato se respeta además: `limit` (20 por defecto, 100 máximo), `items`/`page.nextCursor`,
404 uniforme para inexistente o no publicado, y documentos RFC 7807 con `code`,
`requestId` y `errors`.

## 3. Entidades y rutas migradas

Entidades migradas: **sectors** (detalle) y **cases** / **insights** (listado).

| Ruta | Antes | Ahora |
|---|---|---|
| `/sectores/industria` … `/sectores/banca-seguros` (8) | `RouteStub` siempre | contenido del CMS si el sector está publicado; si no, misma plantilla de arquitectura de antes |
| `/casos` | sólo `CONTENT_REQUIRED` + filas por línea de negocio | lista de casos publicados (si existen) + marcador si no hay ninguno |
| `/insights` | sólo `CONTENT_REQUIRED` + filas por categoría | lista de insights publicados (si existen) + categorías intactas |

Migración **aditiva**: ninguna URL cambia, ningún `metadata` cambia, ningún `robots`
cambia, ningún enlace interno apunta a una ruta nueva. Sin contenido publicado en el CMS
el HTML resultante es equivalente al anterior (verificado en el build: el API no es
alcanzable desde este entorno y las 55 rutas se prerenderizaron igual).

Entidades **no** migradas todavía y por qué:

- `pages` (home): D61 en el registro de decisiones — construir la home desde bloques del
  CMS exige renderizar bloques y media (D45/D46/D48), fuera del alcance de F3.2.
- `universes`, `services`, `products`: existe el endpoint, pero el **mapeo entre slug del
  CMS y URL pública** de esas entidades no está decidido (D15/D24) y esos árboles tienen
  páginas con contenido propio. Migrarlos exigiría inventar el mapeo → `REQUIRES_PROEFEX_INPUT`.
- `heroMedia`/`gallery` en general: la media del CMS llega por URL absoluta y el sistema de
  media real (Doc 13, binding `IMAGES`, D45/D48) sigue pendiente; configurar hosts remotos
  adivinados en `next.config.ts` sería especulativo. Por eso `SectorDetailView` no renderiza
  `heroMedia` todavía.

## 4. Rutas que permanecen estáticas, y por qué

Las **55 rutas del build siguen prerenderizadas** (`○ Static`). La capa de datos usa
`cache: "force-cache"`: si el API no responde o un recurso no está publicado, la página
cae a su plantilla/estado actual en lugar de convertirse en dinámica. Consecuencias:

- sin riesgo de degradar SEO/CWV por SSR no previsto;
- sin dependencia del API en runtime mientras A5 no esté habilitado;
- cuando el contenido se publique, se incorporará mediante revalidación **en build**
  hasta que A5 proporcione la invalidación (ver §7).

Datos consultados en build (por eso y no en runtime):
`/casos` (`content:cases`), `/insights` (`content:insights`) y los 8 sectores.

## 6. Errores, correlación y seguridad

| Situación | `outcome` | Comportamiento |
|---|---|---|
| 200 válido | `ok` | Renderiza contenido del CMS |
| 304 | — | `notModified`: el llamante conserva su copia (nunca se renderiza `null`) |
| 404 (inexistente o no publicado) | `not-found` | Fallback local de la página |
| 401/403/405/413/415/422 | `unavailable` | Fallback local |
| 429 / 5xx / 502 / 503 | `unavailable` (retryable) | Fallback local |
| Timeout / red | `unavailable` (retryable) | Fallback local |
| Cuerpo fuera de contrato / no-JSON / HTML | `invalid-response` | Fallback local; nunca se renderiza un objeto no verificado |
| API sin configurar | `unconfigured` | Fallback local y **ni una petición de red** |
| Slug fuera del patrón del contrato | `bad-request` | Rechazo local antes de salir |

Ninguna función de dominio lanza: la página decide. Los fallos **no se ocultan**: se
registran como `console.warn` con `describeApiError` (`kind`, `status`, `code`, `path`,
`requestId`) sin cuerpos de respuesta, sin cabeceras de firma y sin PII (AGENTS §46).

Correlación: cada lectura envía un `X-Request-Id` **determinista**
(`web.content.<clave>`, p. ej. `web.content.sectors.industria`). Los headers forman parte
de la clave del Data Cache de Next, así que un id aleatorio por lectura invalidaría el
cache en cada build; `tests/content-domain.test.ts` fija esa estabilidad. En las
respuestas prevalece el id **reportado por el API** (`X-Request-Id` de respuesta o
`requestId` del RFC 7807) cuando existe, que es el que quedó en su log. En render
dinámico futuro (A5) la página reenviará el `X-Request-Id` entrante.

Seguridad: la Web sólo consume el contrato público del API. No hay service role, ni
credenciales, ni `NEXT_PUBLIC_*` nuevos, ni acceso directo a Supabase, ni secretos en
código cliente (verificado con `rg` sobre `src`).

## 7. Estrategia de tags preparada para A5

`src/lib/content/tags.ts` reproduce **exactamente** los tags que `proefex-api` deriva
(`modules/webhooks/cache-tags.ts`):

```
content:<tipo>                 content:cases
content:<tipo>:<slug|home>     content:cases:planta-industrial · content:pages:home
content:navigation             (singleton)
content:settings               (singleton)
```

Cada función de dominio devuelve `tags` en su resultado, así que activar A5 no requiere
rehacer la capa de datos:

1. pasar `tags` a `fetch(..., { next: { tags } })` en una única línea de
   `src/lib/api/client.ts`;
2. implementar `/api/revalidate` con el catálogo **cerrado** de tags del contrato, firma
   `X-Proefex-Signature: t=<unix>, v1=<hex>`, ventana anti-replay de 300 s, validación de
   payload y tamaño;
3. provisionar la infraestructura (R2 incremental cache + tag cache) **en
   `proefex-infrastructure`**, y configurarla en `open-next.config.ts`.

Nada de eso se implementa aquí. `content:navigation` y `content:settings` ya están
derivados aunque el CMS aún no los emita: el catálogo es el mismo que publicará el API.

## 8. Configuración por entorno

| Entorno | `PROEFEX_API_BASE_URL` | Default |
|---|---|---|
| development | opcional | `http://localhost:8787/v1` (`wrangler dev` de `proefex-api`) |
| staging | **obligatorio** | **no existe** — `proefex-api` no declara entorno staging; no se inventa |
| production | opcional | `https://api.proefexperu.com/v1` (A2, dominio aprobado) |

`PROEFEX_API_ENV` selecciona el entorno y tiene prioridad sobre `NODE_ENV`; un valor
desconocido se ignora. Una base URL inválida (no absoluta, no http/https, con credenciales,
con query o fragmento) deja el cliente **deshabilitado** en lugar de apuntar a un destino
adivinado. La URL del API vive en un único módulo: no hay `api.proefexperu.com` disperso
por el código.
